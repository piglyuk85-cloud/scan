# Раздел 2. Проектирование программного модуля

## 2.1. Разработка модели данных

Для проектируемой системы учёта экспонатов фонда худграфа нужна одна общая модель данных: метаданные экспонатов, связи с научными руководителями, и чтобы инфраструктуру не раздувать. Выбор в итоге пал на связку SQLite плюс Prisma [4]. База в виде одного файла на диске, а поверх неё со стороны Node.js — объектно-реляционный слой (ORM). Тут есть нюанс. PostgreSQL или MySQL обычно крутят как отдельный сервис: пользователи, бэкапы, сеть. Для локального фонда ВГУ, когда приложение стоит в стенах факультета или на университетском сервере и пользователей одновременно немного, такой масштаб лишний. SQLite отдельного демона не просит — база лежит файлом, тот же процесс Next.js её открывает через драйвер. Развернуть — скопировал файл БД, прописал путь в переменной окружения. Бэкап — тупо копия файла. Для заказчика с точки зрения администрирования это плюс: не надо отдельно ставить и настраивать СУБД [9]. Prisma даёт типизированный клиент под TypeScript, миграции схемы, запросы без голого SQL — разработка быстрее, при изменении структуры таблиц меньше шанс накосячить [4].

В структуре данных заложены три основные сущности. Главная — **Exhibit** (экспонат). В ней планируется хранить: уникальный id (UUID), инвентарный номер фонда, название, краткое описание для карточки и полное (история, техника, контекст), дату создания, данные об авторе (ФИО, курс, группа), ссылку на научного руководителя (внешний ключ на Supervisor), размеры, где сейчас хранится, категорию, год. Для 3D и QR в модель заложены поля: путь к файлу 3D-модели (modelPath — по сути ссылка на .glb или .gltf), флаг has3DModel, путь к превью, плюс путь или id сгенерированного QR (либо файл QR лежит в отдельной папке с именем по id экспоната). Ещё поля под виртуальную галерею: координаты в 3D-сцене (galleryPositionX, Y, Z), масштаб и поворот (galleryScale, galleryRotationY), флаг видимости в галерее. Списки картинок, теххарактеристик и связанных экспонатов планируется держать в JSON-строках — массивы или объекты, чтобы не плодить десятки таблиц при нашем наборе запросов. Вторая сущность — **Supervisor** (научный руководитель): id, ФИО, должность, звание, кафедра. Связь один ко многим: один руководитель — много экспонатов. Нормализация даёт не дублировать ФИО и должность в каждой Exhibit и при смене данных руководителя поменять в одном месте. Третья — **PageContent** (синглтон под редактируемый контент страниц: главная, «О проекте» и т.д.), чтобы куратор мог править тексты без правок кода.

Критичный момент — где хранить сами 3D-модели. Если по правде, пихать бинарники .glb (бывает по десятку мегабайт) в БД как BLOB — плохая затея. База раздувается, бэкапы тяжёлые, выборка «все экспонаты с превью» тянет гигабайты. В проектируемой системе 3D будут лежать в файловой системе (каталог storage/models или public/models), а в БД — только путь (modelPath). Клиент и API отдают путь; браузер по URL тянет файл. Нагрузка на БД остаётся на метаданных, раздача больших файлов — на веб-сервер или Next.js, для нашего масштаба хватает. То же с картинками и сгенерированными PNG с QR: файлы на диске, в БД ссылки. Итоговая схема сущностей ниже в таблице.

*Таблица 2.1.1 — Основные сущности модели данных*

| Сущность   | Назначение                                                                 | Ключевые поля (кратко)                                                                 |
|------------|-----------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| Exhibit    | Карточка экспоната, учёт, привязка к медиа и галерее                       | id, title, description, modelPath, previewImage, supervisorId, galleryPositionX/Y/Z…   |
| Supervisor | Справочник научных руководителей                                            | id, name, position, rank, department                                                    |

Миграции схемы планируется вести через Prisma (prisma migrate): каждое изменение модели — отдельная миграция, при развёртывании у заказчика БД однозначно приводится к актуальному виду [4].

## 2.2. Проектирование сценариев использования

Сценарии использования (use cases) проектируемой системы делятся на две роли: посетитель и администратор (куратор фонда). Распишу по шагам.

**Посетитель.** Старт — человек в выставочном зале перед экспонатом. Под работой или рядом висит табличка с QR. Пользователь достаёт смартфон и сканирует код камерой. Либо через встроенную страницу сканирования на самом сайте: открыл сайт галереи, зашёл в «Сканировать QR», дал доступ к камере и навёл на код. В QR зашит URL карточки экспоната, что-то вроде `https://site.example/exhibit/[id]`, где `[id]` — уникальный идентификатор экспоната (UUID). Браузер уходит по этому адресу. Серверная часть (Next.js) по маршруту `/exhibit/[id]` вытаскивает из URL параметр `id`, дергает БД через Prisma — экспонат с таким id — и если запись есть и экспонат публичный, отдаёт страницу. На странице рендерятся название, автор, описание, галерея фото и если есть 3D — интерактивный блок просмотра. В этом блоке клиент (React) поднимает сцену Three.js, хук useGLTF по modelPath запрашивает .glb с сервера и выводит модель; пользователь пальцем или мышью крутит камеру вокруг объекта (OrbitControls). Полный путь от скана QR до «кручу 3D» выглядит так: скан QR → переход по URL с id → сервер по id отдаёт данные экспоната и HTML → клиент рендерит карточку и по modelPath тянет .glb → модель грузится и показывается в канвасе, жесты обрабатывает библиотека. Обработка id из URL тут центральна: один маршрут `/exhibit/[id]` обслуживает любой экспонат, идентификация только по id, без зашитых под каждую работу страниц.

**Администратор.** Сценарий «наполнение фонда». Куратор заходит в закрытый раздел (админ-панель), жмёт «Добавить экспонат», заполняет форму: название, автор, описание, категория, научрук из выпадающего списка, размеры, место хранения и т.д., грузит фотки и при необходимости файл 3D (.glb/.gltf). Файл сохраняется на сервере в файловое хранилище, в БД пишется путь. После «Сохранить» бэкенд кроме записи в БД планирует вызвать логику генерации QR. В проектируемой системе предусмотрен встроенный Python-скрипт: по id экспоната он собирает URL карточки, генерирует картинку QR в PNG и кладёт файл в заданную папку (например qr-codes/[id].png). Бэкенд после сохранения экспоната дергает эту Python-логику — передаёт id скрипту; скрипт пишет готовый PNG в папку. Куратор может сразу скачать или распечатать QR и повесить под экспонатом в зале. В итоге процесс замкнут: добавил экспонат, залил медиа, сохранил — получил QR для печати без ручного кодирования ссылок. Ещё сценарии администратора: правка и удаление экспонатов, настройка позиций в виртуальной галерее (координаты, масштаб, поворот), правка текстов страниц сайта.

## 2.3. Выбор программного обеспечения и технологического стека

Стек проектируемой системы подбирался под задачу: одно веб-приложение с каталогом, 3D-просмотром и админкой, которое можно развернуть у заказчика без лишней сложности.

**Next.js [1]** взят как фуллстек-фреймворк. В одном проекте и серверная и клиентская часть: маршрутизация (в том числе динамические маршруты типа `/exhibit/[id]`), API Routes под бэкенд (эндпоинты под экспонаты, загрузку файлов, контент страниц), серверный рендеринг или статика, плюс клиент на React. Отдельный сервер API и отдельное SPA поднимать не надо — один процесс Next.js и страницы и API отдаёт, развёртывание и конфиг проще. Документация и экосистема Next заточены под production-сборку и деплой [1], что как раз под требование «передать заказчику рабочее решение».

**React Three Fiber (R3F) [7]** и библиотека **Drei** (доки в той же экосистеме pmnd.rs) выбраны под 3D в браузере. R3F — это по сути рендерер Three.js в виде React-компонентов: сцену, камеру, свет и объекты описываешь декларативно в JSX, а не императивным кодом на голом Three.js. Так проще встроить 3D в состояние React — пропсы, список экспонатов, маршруты. Drei даёт готовые штуки: OrbitControls чтобы крутить камеру вокруг объекта, useGLTF чтобы грузить модели в формате glTF/GLB. Хук **useGLTF** [5, 7] как раз и делает «загрузить .glb по URL и отдать сцену в сцену Three.js». Модель запрашивается по HTTP, браузер парсит glTF/GLB и строит меши, материалы, текстуры. Нюанс с размером. Модели до нескольких десятков мегабайт (скажем до 50 МБ) в принципе грузятся, но на мобильном интернете в стенах вуза это может вылиться в долгое ожидание. Поэтому в проектируемой системе планируется ограничить рекомендуемый размер загружаемых моделей (например до 50 МБ) и на клиенте сделать индикатор загрузки — лоадер или прелоадер, чтобы пользователь видел что модель подгружается, а не пялился в пустой экран. Для мобильного трафика это критично: тяжёлые файлы люди не ждут и закрывают вкладку; легковесные модели плюс явный прогресс загрузки опыт улучшают.

От тяжёлых движков вроде Unity для веба отказались сознательно. Unity (в том числе WebGL-экспорт) тянет за собой огромный рантайм и объём только на «движок»; для сценария «показать одну статическую или почти без анимации модель и дать её покрутить» это перебор. Three.js и R3F позволяют собрать тонкий клиент — грузится только то что нужно для сцены и одной модели. В общем для простого веб-просмотра экспонатов связка Three.js + R3F + Drei выглядит адекватно.

**Tailwind CSS [8]** взят под стилизацию. Утилитарный подход (классы вроде flex, p-4, text-gray-800) даёт быструю вёрстку без размазывания стилей по кучке CSS-файлов и при этом визуал можно держать сдержанным. Для каталога и карточек экспонатов важно чтобы интерфейс не отвлекал от самого искусства: нейтральные цвета, нормальная типографика, акцент на контенте — фото, 3D, текст. Tailwind как раз даёт задать такую систему отступов и цветов без лишнего декора.

**TypeScript [3]** по всему проекту под типизацию: модели данных (типы экспоната, пропсы компонентов), ответы API, параметры маршрутов. Меньше ляпов на этапе разработки и проще рефакторить когда схема данных меняется.

## 2.4. Технические требования и архитектура системы

Архитектура проектируемой системы трёхуровневая. Клиент (браузер) получает HTML, CSS и JS-приложение на React и Three.js; при необходимости дергает API (список экспонатов, один экспонат по id, загрузка файлов) и тянет статику — картинки, файлы .glb. Серверная часть — в рамках Next.js: API Routes обрабатывают HTTP-запросы, ходят в базу через Prisma и отдают JSON или файлы. База данных — SQLite файлом на диске; к ней обращается только процесс Next.js. Схематично: **Клиент (React / Three.js) ↔ API (Next.js) ↔ БД (SQLite)**. Файловое хранилище (3D, картинки, сгенерированные QR) стоит на том же сервере; доступ к файлам по URL через Next.js или раздачу статики.

*Рисунок 2.4.1 — Архитектура системы (рекомендуется вставить схему: Браузер → Next.js (API + статика) → SQLite; Next.js ↔ файловое хранилище).*

К требованиям к клиенту относится обязательная поддержка WebGL в браузере. Без WebGL Three.js 3D не покажет. Современные браузеры на десктопе и смартфонах (Chrome, Safari, Firefox, Edge) WebGL умеют; в требованиях к проектируемой системе закладывается проверка поддержки (или сообщение «Ваш браузер не поддерживает 3D») и рекомендация использовать свежую версию браузера. На мобильных дополнительно учитывается память и размер моделей: тяжёлые сцены могут подвисать или падать на слабых устройствах, поэтому рекомендация по весу модели (например до 50 МБ) и наличие прелоадера остаются в технических требованиях.

Как система будет вести себя при загрузке тяжёлых моделей (порядка 50 МБ). Пока .glb запрашивается и парсится, пользователь не должен смотреть в пустой экран. В проектируемой системе будет обеспечен индикатор загрузки — лоадер, спиннер или прогресс-бар в блоке 3D-просмотра. После успешной загрузки и парсинга индикатор убирается и показывается сцена с моделью. При ошибке (сеть, битый формат, слишком большой размер) планируется показывать сообщение об ошибке и по возможности предложить обновить страницу или перейти к остальному контенту карточки. То есть требование «не оставлять пользователя без обратной связи при долгой загрузке» заложено в проектирование интерфейса 3D.

Требования к серверу при развёртывании: возможность запуска Node.js (LTS), достаточно диска под базу SQLite и файловое хранилище (модели, картинки, QR), при необходимости — обратный прокси (например nginx) перед Next.js под HTTPS и раздачу статики. Отдельного железа под БД не нужно — SQLite работает в процессе приложения.

## Выводы по разделу 2

В разделе спроектирован программный модуль. Выбрана модель данных на SQLite и Prisma с сущностями Department, Exhibit, Student, Category, MediaResource, GallerySettings, Supervisor и PageContent. 3D и медиа вынесены в файловое хранилище, в БД только ссылки. Спроектированы варианты использования и диаграммы потоков данных сценарев для посетителя (путь от скана QR до просмотра 3D по id из URL) и администратора (наполнение фонда, генерация QR через вызов Python-скрипта после сохранения экспоната). Обоснован стек: Next.js как фуллстек, React Three Fiber и Drei для 3D с загрузкой моделей через useGLTF, ограничения по размеру моделей и прелоадер для мобильного трафика, Tailwind под нейтральный интерфейс, отказ от тяжёлых движков (Unity) для веба. Зафиксирована архитектура системы и технические требования: WebGL на клиенте, индикация загрузки при тяжёлых моделях, требования к серверу. Раздел даёт основание перейти к реализации (раздел 3).
