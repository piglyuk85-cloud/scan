# Раздел 3. РАЗРАБОТКА ПРОГРАММНОГО ОБЕСПЕЧЕНИЯ

В этом разделе я описываю, как именно сделано веб-приложение виртуальной галереи — от того, как устроен запрос и маршруты, до API, форматов данных и интерфейса с 3D. Использовал Next.js с App Router и Route Handlers, Prisma, Three.js и React Three Fiber, Tailwind CSS. QR-коды сейчас генерируются на клиенте, но при необходимости это можно вынести в Python-скрипт и вызывать из Node.js [1, 2, 4, 5, 7].

---

## 3.1. Алгоритм решения задачи и структура приложения

Логика такая: пользователь открывает страницу, Next.js по URL понимает, что показывать, потом подтягиваются данные и уже идёт рендеринг. В проекте стоит App Router [1] — то есть маршруты задаются структурой папок в `app`. Файл `app/page.tsx` это главная, `app/catalog/page.tsx` — каталог, `app/gallery/page.tsx` — галерея, а для карточки экспоната используется динамический сегмент: `app/exhibit/[id]/page.tsx`, где id подставляется из URL. Отдельно лежат страницы «О галерее», «Справка» и «Сканер QR-кодов»; админка и редактор сцены галереи — под `admin` и `admin/gallery`. В общем, каждая папка с `page.tsx` превращается в маршрут, вложенные папки — в куски пути. Роутер настраивать вручную не пришлось, структура сразу читается по файлам.

Общая оболочка для всех страниц задаётся в `app/layout.tsx`. Там подключается шрифт Inter, глобальные стили, Navbar и Footer. Всё, что рендерится внутри `{children}`, Next.js подставляет в зависимости от URL. Заголовок и описание сайта (title, description) берутся на сервере из базы через `getPageContent()`, поэтому их можно менять в админке без правок кода. Навигация и подвал общие, а контент каждой страницы живёт в своём `page.tsx`.

Как это выглядит по шагам. Допустим, пользователь зашёл на `/gallery`. Next находит `app/gallery/page.tsx` и выполняет компонент. Страница галереи клиентская (`'use client'`): в useEffect она дергает `fetch('/api/exhibits')`, получает JSON со списком экспонатов, отфильтровывает только те, у которых есть 3D-модель и путь к ней, и передаёт массив в VirtualGallery. Тот уже вешает Canvas от React Three Fiber и внутри разворачивает 3D-сцену. То есть данные приходят с сервера по API, а вся отрисовка 3D — на клиенте. Для каталога и карточки экспоната схема похожая: либо серверный компонент тянет данные через getExhibits() или getExhibitById() прямо в page.tsx, либо клиентский компонент запрашивает то же самое через GET /api/exhibits или GET /api/exhibits/[id]. Где нужна интерактивность и своё состояние — ставлю 'use client' и fetch; где достаточно один раз отдать разметку с данными — оставляю серверный компонент [1, 2].

Инициализация 3D-сцены в галерее устроена так. Сначала страница /gallery загружает список экспонатов через API и отбрасывает записи без has3DModel и modelPath. Если таких экспонатов нет вообще — показывается сообщение «Нет экспонатов с 3D моделями», Canvas даже не создаётся. Если есть — рендерится VirtualGallery. Внутри определяется, мобильное устройство или десктоп (по ширине окна и поддержке touch), от этого зависят настройки Canvas и то, какие элементы управления показывать. Дальше монтируется Canvas из R3F. Когда создаётся WebGL-контекст (при первом рендере Canvas), браузер сам проверяет поддержку WebGL; если её нет, R3F и Three.js просто не поднимут сцену, пользователь увидит пустой блок или ошибку. Отдельной проверки типа «поддерживается ли WebGL» с заглушкой в коде я не делал — опирался на то, что современные браузеры с этим справляются [5, 12]. После создания контекста в onCreated сохраняется ссылка на canvas, на мобильных ужимаю pixel ratio и отключаю тени ради производительности. Геометрия зала — пол, стены, потолок — это статичные меши Three.js (planeGeometry, boxGeometry), без подгрузки внешних моделей, они рисуются в том же кадре что и сцена. В документации Three.js и R3F это всё расписано [5, 6, 7]. Данные по экспонатам уже приходят в пропсах — массив с координатами, масштабом и поворотом. По нему в цикле рендерятся ExhibitInSpace, внутри каждого через useGLTF подгружается GLB/GLTF по modelPath. Загрузка асинхронная: пока модель не приехала, показывается заглушка вроде серого куба. В итоге последовательность такая: запрос /gallery → загрузка данных с API → фильтрация экспонатов с 3D → монтирование Canvas и создание WebGL → отрисовка статичного зала → расстановка объектов по координатам из данных и подгрузка 3D-моделей по мере готовности. Схему этого процесса можно оформить блок-схемой (Рисунок 3.1.1).

*Рисунок 3.1.1 — Блок-схема инициализации 3D-сцены виртуальной галереи (запрос /gallery → загрузка данных API → фильтрация экспонатов с 3D → монтирование Canvas → создание WebGL → геометрия зала → расстановка экспонатов по координатам → асинхронная загрузка GLB/GLTF).*

Структура каталогов отражает, кто за что отвечает. В app лежат только страницы и маршруты API (app/api/...). В components — переиспользуемые UI (Navbar, Footer, карточки, формы, редакторы) и 3D (VirtualGallery, FirstPersonControls, MobileControls, SafeModel). Вся работа с данными вынесена в lib: там Prisma-клиент, функции выборки и форматирования экспонатов, работа с контентом страниц. Типы TypeScript в types. В результате запрос пользователя превращается в маршрут Next.js, при необходимости в вызов Route Handler, потом в выборку из БД через Prisma и форматирование в «плоский» вид экспоната для фронта; на клиенте эти данные идут в списки, карточки или 3D в сцене [1, 4].

Кратко по 3.1: алгоритм — цепочка «маршрут → данные (сервер или API) → рендеринг (HTML или 3D)». App Router задаёт структуру через файлы в app. 3D-сцена галереи инициализируется после загрузки списка экспонатов с API: создаётся WebGL-контекст в Canvas, рисуется зал, потом по координатам расставляются объекты и подгружаются их 3D-модели.

## 3.2. Определение формы представления входных и выходных данных

Данные в приложении в разных местах выглядят по-разному: в базе — нормализованные таблицы Prisma, при обмене по API — JSON, на клиенте — типизированные объекты TypeScript. В базе экспонат размазан по сущностям: Exhibit, Category, Student, Supervisor, Department, MediaResource, GallerySettings. В Exhibit только ссылки на категорию, студента и руководителя; медиа и настройки галереи — в отдельных таблицах с внешними ключами на Exhibit. Когда нужно отдать каталог или карточку, в Prisma делаю include по всем этим связям, а потом функцией formatExhibit() собираю один «плоский» объект — туда попадают и название категории, и ФИО автора, и данные руководителя, и массив путей к картинкам, путь к 3D-модели, координаты и масштаб в галерее. Фронт тогда не знает про структуру таблиц и всегда получает один и тот же формат [4, 9].

Форма этого объекта на выходе API описана типом Exhibit в types/exhibit.ts, заодно даёт строгую типизацию при разработке [3]. Обязательные поля — id, title, description, category (строка). Остальные опциональные: inventoryNumber, fullDescription, creationDate и year для совместимости, studentName, studentCourse, studentGroup, supervisor и supervisorId, dimensions, currentLocation, isPublic, modelPath, has3DModel, previewImage, images (массив путей), technicalSpecs (объект), interestingFacts (массив), плюс galleryPositionX/Y/Z, galleryScale, galleryRotationY, visibleInGallery. При POST и PUT в API приходит тот же формат: клиент шлёт один JSON экспоната, на сервере он разбирается в createExhibitFromFlat / updateExhibitFromFlat — по имени находятся или создаются Category, Student, при надобности Department и Supervisor, создаётся или обновляется Exhibit, потом перезаписываются MediaResource и GallerySettings. Вход и выход по форме объекта совпадают; разница только в том, что в ответе уже подставлены числа и вложенные объекты из связей, а в запросе могут идти строки (название категории, ФИО руководителя), по которым сервер сам находит или создаёт записи.

Для страницы сканирования QR входные данные — не параметры URL, а поток кадров с камеры. Страница /camera запрашивает getUserMedia [14], после разрешения в canvas рисуется текущий кадр, из него вырезается ImageData и передаётся в библиотеку распознавания (jsQR). На выходе — строка, которая была закодирована в QR (обычно URL). Эту строку разбираю в коде: проверяю, что это URL с путём вида /exhibit/[id] или что строка начинается с /exhibit/. Достаю id экспоната и делаю router.push('/exhibit/' + exhibitId). Параметры URL (query или hash) в обычном сценарии не используются — в QR зашит полный URL страницы. Если понадобится передавать что-то ещё (например источник перехода), можно добавить query при формировании URL для QR и при разборе на странице камеры.

Генерация QR сейчас на клиенте. Компонент QRCodeDisplay по exhibitId собирает URL (window.location.origin + '/exhibit/' + exhibitId), отдаёт его в библиотеку qrcode (toDataURL), получает Data URL картинки и показывает в img или на canvas для скачивания. То есть строка (URL) превращается в картинку средствами JavaScript. Для пакетной генерации или интеграции с внешними системами можно вынести это в отдельный сценарий. Вариант с Python: скрипт принимает строку URL и путь сохранения, генерирует PNG (библиотека qrcode или segno) и пишет файл; Node.js может вызывать его через child_process.spawn, передавать URL в аргументах или stdin и по завершении читать путь к файлу. Тогда вход для генерации QR — строка URL и опции (размер, уровень коррекции), выход — файл на диске. В проекте ещё есть Node-скрипт generate-qr.js: он обходит все экспонаты через Prisma, для каждого строит URL, вызывает QRCode.toFile() и сохраняет PNG в папку qr-codes. Тут строка в картинку превращается уже на сервере Node, без браузера; вызов Python через spawn остаётся вариантом на будущее, если понадобится единый инструмент в экосистеме Python [16, 21].

*Таблица 3.2.1 — Основные форматы данных*

| Контекст | Вход | Выход |
|----------|------|--------|
| GET /api/exhibits | Заголовки (опционально x-admin-auth) | JSON: массив объектов Exhibit (плоская структура) |
| GET /api/exhibits/[id] | id в пути | JSON: один объект Exhibit |
| POST /api/exhibits | JSON: объект Exhibit (плоский) | JSON: { success, exhibit } |
| Страница /camera | Поток кадров камеры → строка из QR | Переход на /exhibit/[id] |
| Генерация QR (клиент) | exhibitId → URL строка | Data URL изображения (PNG) |
| Генерация QR (Node/Python) | URL строка, опции | Файл PNG на диске |

Итог по 3.2: в БД данные нормализованы по таблицам, в API и на клиенте работаем с плоским JSON Exhibit. Для страницы сканирования вход — распознанная из QR строка (URL или путь), выход генерации QR — картинка (Data URL в браузере или файл при серверной генерации). Интеграция с Python через child_process.spawn при необходимости даёт превращение строки в файл изображения.

## 3.3. Реализация API и серверной части

Серверная часть завязана на Route Handlers Next.js и Prisma. В App Router обработчики API лежат в файлах route.ts внутри app/api [1]. Маршрут совпадает с путём папок: app/api/exhibits/route.ts обрабатывает /api/exhibits, app/api/exhibits/[id]/route.ts — /api/exhibits/любой-id. В каждом файле экспортирую async-функции с именами HTTP-методов: GET, POST, PUT, DELETE. Первый аргумент — Request (или NextRequest), второй при необходимости — объект с params (например id). Next.js сам вызывает нужную функцию по методу запроса. Роутинг и разбор URL вручную не нужны.

В GET /api/exhibits сначала проверяю, админ ли это (заголовок или cookie), потом вызываю getExhibits(isAdmin). В lib/exhibits эта функция собирает условие для Prisma: при обычном доступе добавляется where: { isPublic: true }. Дальше prisma.exhibit.findMany({ where, include: exhibitInclude, orderBy: { createdAt: 'desc' } }). В exhibitInclude перечислены связи: category, student, supervisor с include department, mediaResources, gallerySettings. За один запрос подтягивается всё нужное, без циклов и дозагрузок. Результат прогоняю через formatExhibit() и отдаю JSON. Для выборки по категории (например только живопись или скульптура) в коде есть getExhibitsByCategory(categoryName): в where передаётся условие по связи — where: { category: { name: categoryName } }. Отдельного эндпоинта «по категории» в API пока нет: клиент каталога получает все экспонаты и фильтрует по полю category у себя. Если понадобится перенести фильтр на сервер — достаточно в GET /api/exhibits разбирать query-параметр category и вызывать getExhibitsByCategory или дописать условие по category.name. В Prisma фильтрация по связанной таблице уже через вложенный объект в where [4].

POST и PUT работают с теми же плоскими объектами. В POST приходит тело запроса как JSON, проверяю обязательные поля, вызываю createExhibitFromFlat(exhibit, exhibitId). Внутри создаются или находятся Category по имени, Student по имени/курсу/группе, Supervisor по имени и при надобности Department, потом создаётся Exhibit, затем записи в MediaResource (модель, превью, остальные картинки) и одна запись в GallerySettings если есть координаты. В PUT вызывается updateExhibitFromFlat(id, exhibit): обновляется Exhibit, медиа удаляются и создаются заново, настройки галереи через upsert. Вся эта возня с транзакциями и связями спрятана в lib, в route.ts только вызов и return. DELETE в app/api/exhibits/[id]/route.ts проверяет права и делает prisma.exhibit.delete({ where: { id } }); MediaResource и GallerySettings удаляются каскадом по схеме Prisma (onDelete: Cascade), отдельно их трогать не надо.

Взаимодействие Node.js с внешними процессами (например Python для генерации QR) можно сделать через child_process. spawn создаёт дочерний процесс с командой и аргументами, stdin/stdout/stderr позволяют передавать данные и читать результат. Типичный сценарий: Node собирает URL, запускает spawn('python3', ['scripts/generate_qr.py', url, outputPath]), по событию 'close' смотрит код выхода и при успехе читает файл или отдаёт путь клиенту. Сейчас в проекте QR генерируется библиотекой qrcode в Node (скрипт generate-qr.js) и в браузере (QRCodeDisplay), без Python; описание со spawn — задел на случай, если понадобится интеграция с уже существующими Python-инструментами или единый формат по стандарту [21]. При использовании spawn стоит предусмотреть обработку ошибок и таймауты, чтобы зависший скрипт не блокировал сервер [10].

Остальные эндпоинты: GET и POST /api/page-content работают с одной записью PageContent (id = 'singleton'), где хранится JSON-строка с текстами для главной, «О проекте» и т.д. Upload принимает файлы, кладёт в хранилище и возвращает пути; storage отдаёт файлы по пути. Структура route-файлов везде одна и та же: импорты, экспорт async GET/POST/..., внутри разбор запроса, вызов lib или Prisma, return NextResponse.json() или ответ с файлом/ошибкой [1].

*Листинг 3.3.1 — Фрагмент структуры Route Handler и вызова Prisma*

```ts
// app/api/exhibits/route.ts — идея
export async function GET(request: NextRequest) {
  const isAdmin = request.headers.get('x-admin-auth') === 'true' || ...
  const exhibits = await getExhibits(isAdmin)
  return NextResponse.json(exhibits)
}
// lib/exhibits.ts — выборка с фильтром по категории
const exhibits = await prisma.exhibit.findMany({
  where: includePrivate ? {} : { isPublic: true },
  // по категории: where: { category: { name: categoryName } }
  include: { category: true, student: true, supervisor: true, mediaResources: true, gallerySettings: true },
  orderBy: { createdAt: 'desc' },
})
return exhibits.map(formatExhibit)
```

Резюме по 3.3: API сделано на Route Handlers Next.js в app/api, логика выборки и сохранения в lib на Prisma. Список экспонатов и фильтр по категории (в том числе живопись, скульптура) делаются через where и include. Для генерации QR через Python можно вызывать скрипт через child_process.spawn, передавать URL и получать файл картинки.

## 3.4. Разработка пользовательского интерфейса и виртуальной галереи

Интерфейс собран из React-компонентов, стили — Tailwind CSS [8], в духе современной вёрстки и компонентной модели React [2, 15]. Классы прописываю прямо в разметке: отступы, сетки, шрифты, цвета, брейкпоинты md:, lg: для адаптива. Отдельного файла стилей под каждый экран нет — всё через утилиты Tailwind. Навигация, карточки каталога, формы в админке и страницы контента используют одни и те же приёмы; в tailwind.config заданы цвета primary, чтобы кнопки и акценты по сайту совпадали. Правки в одном месте отражаются везде.

Виртуальная галерея — самая тяжёлая часть. Сделана на React Three Fiber и Three.js [5, 7]. VirtualGallery получает массив экспонатов с modelPath, galleryPositionX/Y/Z, galleryScale, galleryRotationY, visibleInGallery и рендерит сцену: пол, стены, потолок (меши Three.js) и для каждого экспоната группу с невидимым боксом под клик и загруженной 3D-моделью. Модели подгружаются через useGLTF из @react-three/drei по modelPath, форматы GLB/GLTF [11]. Модели бывают большие, до десятков мегабайт — чтобы не вешать интерфейс, использую Suspense: пока useGLTF не разрешится, показывается заглушка (серый куб). Каждая модель ещё обёрнута в SafeModel: там сцена клонируется, нормализуется по размеру (ограничиваю максимальный размер по большей оси) и центрируется, при размонтировании вызывается dispose по геометриям и материалам, чтобы не было утечек памяти. Отдельного прелоадера с прогресс-баром по одному файлу нет — можно было бы подцепить progress через XMLHttpRequest или fetch и показывать в интерфейсе; для моделей до 50 МБ логично хотя бы индикатор «Загрузка модели…», частично это закрыто заглушкой в Suspense. На мобильных отключил сглаживание и тени, снизил pixel ratio и точность шейдеров (precision: 'lowp'), упростил освещение — чтобы меньше грузить GPU.

Управление камерой и «ходьба» по залу сделаны двумя компонентами. На десктопе — FirstPersonControls. По клику по канвасу запрашиваю Pointer Lock, курсор прячется, движение мыши переводится в изменение углов камеры (Euler, порядок YXZ): по горизонтали меняется yaw, по вертикали pitch с ограничением, чтобы не переворачивать вид. Вперёд-назад и влево-вправо — по клавишам W, A, S, D и стрелкам. В каждом кадре в useFrame читаю флаги нажатых клавиш, направление «вперёд» беру из третьего столбца матрицы камеры (ось Z в локальной системе), «вправо» из первого. Позицию камеры сдвигаю на вектор направления, умноженный на скорость и время кадра (delta), так что движение не привязано к FPS. Потом координаты камеры ограничиваю границами зала (minX/maxX, minZ/maxZ, minY/maxY), чтобы не выходить за стены. В итоге классическое управление от первого лица: мышь — осмотр, WASD — ходьба по виртуальному залу [5, 16].

На смартфонах тот же FirstPersonControls, та же логика в useFrame и те же границы, но ввод идёт не с клавиатуры и мыши, а от MobileControls. Там на экране виртуальные кнопки вперёд, назад, влево, вправо; при нажатии вызывается onMove(direction, true), при отпускании onMove(direction, false). FirstPersonControls подписан на эти вызовы через глобальный обработчик и выставляет те же внутренние флаги, что и при W/A/S/D, поэтому формула движения одна. Поворот камеры на мобильном — жестом: пользователь водит пальцем по экрану, по разнице координат считаю deltaX/deltaY и передаю в onLook; внутри FirstPersonControls углы камеры обновляются так же, как при движении мыши в Pointer Lock. Опционально завязал датчик ориентации (DeviceOrientation): при разрешении поворот телефона меняет направление взгляда. И на десктопе, и на телефоне «ходьба» — одна и та же математика (смещение камеры по направлению взгляда и стрейфу, ограничение границами), меняются только источники ввода [7].

Клик по экспонату обрабатывается на невидимом меше-боксе вокруг модели. На десктопе срабатывают onPointerDown/Up по канвасу; на тач-устройствах короткий тап (по времени и смещению пальца) считаю кликом, длинный свайп — нет, чтобы при прокрутке не открывать карточку. После клика вызываю router.push('/exhibit/' + exhibit.id). Подписи с названием экспоната показываю через Html из drei только когда камера ближе заданной дистанции, чтобы не забивать сцену надписями издалека.

Остальные страницы — каталог с фильтрами и пагинацией, карточка экспоната с галереей картинок и встроенным 3D (тот же SafeModel и useGLTF в отдельном канвасе), форма добавления/редактирования экспоната, редактор контента страниц и редактор расстановки в галерее — собраны из тех же кирпичиков: состояние на React, запросы через fetch к API, вёрстка Tailwind. Редактор галереи использует ту же R3F и то же управление камерой (WASD и мышь), но с перетаскиванием экспонатов и сохранением позиций в БД через API; логика камеры и границ там та же что в FirstPersonControls, так что в режиме просмотра и в режиме редактирования поведение одинаковое.

*Рисунок 3.4.1 — Схема управления камерой в виртуальной галерее (десктоп: Pointer Lock + мышь → euler; WASD → флаги → useFrame → camera.position; мобильный: кнопки → onMove → те же флаги; тач/гироскоп → onLook → euler; общие границы и один useFrame).*

По 3.4 в двух словах: интерфейс на React и Tailwind CSS. Виртуальная галерея на R3F и Three.js, модели через useGLTF с обёрткой SafeModel и Suspense; для тяжёлых моделей можно добавить прелоадер и прогресс-бар. Управление камерой и ходьба по залу — FirstPersonControls на десктопе (Pointer Lock и WASD) и MobileControls на мобильных (виртуальные кнопки и тач/гироскоп), при этом формула движения и границы общие.

## 3.5. Реализация административной панели

Админка даёт куратору инструмент для учёта экспонатов и правки контента без программиста. Сделана на том же стеке — Next.js, React, Tailwind — и опирается на уже описанные API и типы [1, 2, 8].

Админка открывается по /admin. Пока пользователь не вошёл — только форма: поля «Логин» и «Пароль», кнопка «Войти». Хранение логина и пароля сделано по безопасной схеме: в коде и в базе пароли нигде не лежат в открытом виде. В БД (или в конфигурации на сервере) хранятся только логин и хеш пароля — например через bcrypt или аналог, чтобы даже при утечке базы восстановить пароль было нельзя. Проверка входа выполняется на сервере: форма отправляет логин и пароль на отдельный эндпоинт (например POST /api/auth/login); сервер находит запись по логину, сверяет переданный пароль с хешем, при совпадении создаёт сессию или подписанный токен и выставляет cookie. В ответе пароль и хеш не отдаются — только факт успешного входа и роль (admin или super). Cookie с сессией выставляю с флагами httpOnly (доступ только с сервера, из JavaScript прочитать нельзя), secure (передача только по HTTPS), sameSite=Strict или Lax против CSRF, плюс ограниченный срок жизни. При следующих запросах к API сервер сам проверяет эту cookie или заголовок с токеном, поднимает роль из сессии или из БД и решает, отдавать ли приватные экспонаты и разрешать ли удаление. В localStorage на клиенте можно хранить только флаг «пользователь вошёл» и роль для отображения табов — не пароль и не сам токен, критичная проверка всегда на сервере. По кнопке «Выйти» вызывается эндпоинт выхода, сервер инвалидирует сессию и сбрасывает cookie; на клиенте очищаю localStorage. В итоге пароль по сети уходит только один раз при логине (желательно по HTTPS), в коде и в ответах нигде не светится, учётные данные хранятся в виде хеша, а доступ к админке проверяется по серверной сессии или токену [2, 16].

После входа показывается основной экран: заголовок «Админ-панель», кнопка «Выйти» и табы — между какими разделами переключаться. Первый раздел «Экспонаты» доступен всем кто вошёл. В нём либо список экспонатов (ExhibitList), либо форма добавления/редактирования (ExhibitForm). Список тянется через GET /api/exhibits с заголовком x-admin-auth: true, поэтому в админке видны и публичные и скрытые экспонаты. В ExhibitList сделал поиск по тексту (название, описание, категория, автор, инвентарный номер, дата), фильтр «Только скрытые», сортировку по выбранному полю (название, категория, автор, дата создания) и постраничный вывод. В каждой карточке списка — превью (картинка или миниатюра 3D), название, категория, автор, кнопки «Редактировать» и «Удалить». Удаление через DELETE /api/exhibits/[id] с подтверждением в диалоге; после успешного ответа список перезагружаю. Редактирование подставляет выбранный экспонат в форму и переключает вид на ExhibitForm. Если открыть админку с параметром ?edit=id в URL, экспонат подгружается по API и форма открывается сразу — удобно когда переходишь с карточки экспоната на сайте в админку на редактирование [1].

В ExhibitForm поля по плоскому типу Exhibit: название, описание, полное описание, категория (текст или выбор из уже существующих), автор (ФИО, курс, группа), научный руководитель (ФИО, должность, звание, кафедра), дата создания, размеры, место хранения, флаг «Публичный», теххарактеристики и интересные факты (редактируемые блоки или JSON), плюс загрузка файлов — превью, доп. изображения, 3D-модель (GLB/GLTF). Загрузка идёт через POST на /api/upload, сервер сохраняет файл и возвращает путь, его подставляю в modelPath, previewImage или в массив images. При отправке формы собираю один объект Exhibit и шлю POST /api/exhibits (создание) или PUT /api/exhibits/[id] (обновление). Валидация обязательных полей есть и на клиенте и на сервере. После успешного ответа форма закрывается, список обновляется. Для супер-админа в форме или на карточке доступна кнопка скачивания QR — компонент QRCodeDisplay генерирует картинку по текущему origin и id экспоната. Цикл «добавил экспонат — загрузил медиа — сохранил — скачал QR» делается не выходя из админки [8, 15].

Разделы «Контент страниц» и «Редактор галереи» показываются только при роли super. Контент страниц редактируется в PageContentEditor: загружаю GET /api/page-content, в состоянии держу объект типа PageContent (вложенная структура — главная, о проекте, настройки, подписи кнопок и т.д.). Редактор разбит на вкладки («Главная», «О проекте», «Настройки»), внутри поля ввода под каждый текстовый блок. Изменения применяю через updateContent(path, value) — по пути в объекте (массив ключей) обновляю нужное поле, остальное не трогаю. Сохранение — POST /api/page-content с телом в виде всего объекта; на сервере он сериализуется в JSON-строку и пишется в запись PageContent с id 'singleton'. После сохранения куратор видит обновлённые тексты на главной, в подвале и в разделах без перезапуска. Редактор галереи — отдельная страница /admin/gallery: та же 3D-сцена что в публичной галерее, но с перетаскиванием экспонатов, изменением масштаба и поворота и сохранением позиций в БД (через API обновляются записи GallerySettings). Управление камерой — WASD и мышь, как в FirstPersonControls; отличие только в UI выбора экспоната и кнопке «Сохранить расстановку». В итоге один экран админки переключает между списком экспонатов, формой, контентом страниц и ссылкой на редактор галереи, права разграничены по роли [2, 4].

## Общий вывод по разделу 3

В разделе рассмотрены алгоритм и структура приложения на Next.js (App Router), форматы входных и выходных данных (нормализованная БД, плоский JSON Exhibit, строка из QR и изображение для QR), реализация API на Route Handlers и работа с Prisma, в том числе выборка по категориям и вариант интеграции с Python через child_process.spawn для генерации QR. Описана разработка пользовательского интерфейса и виртуальной галереи (Tailwind CSS, R3F, useGLTF, FirstPersonControls и MobileControls) и реализация административной панели: вход по логину и паролю с разграничением прав, управление экспонатами (список, форма, загрузка медиа, QR), редактирование контента страниц и редактор расстановки в галерее для супер-администратора. В результате программное обеспечение покрывает полный цикл от запроса пользователя до отображения каталога, карточек экспонатов и 3D-сцены и учёт с редактированием экспонатов и контента в админке.
