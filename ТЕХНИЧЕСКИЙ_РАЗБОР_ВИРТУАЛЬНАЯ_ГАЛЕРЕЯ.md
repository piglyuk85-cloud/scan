# Технический разбор: Виртуальная галерея и редактор галереи

## 1. Связь 3D и БД (GallerySettings → Three.js)

**Откуда берутся данные:** В БД таблица `GallerySettings` хранит `posX`, `posY`, `posZ`, `scale`, `rotY`, `visibleInGallery` (связь 1:1 с `Exhibit`). При чтении в `lib/exhibits.ts` функция `formatExhibit()` маппит их в плоский тип `Exhibit`: `galleryPositionX/Y/Z`, `galleryScale`, `galleryRotationY`, `visibleInGallery`.

**Как попадают в сцену:** Глобального стейта (Zustand/Redux) нет. Всё идёт через **пропсы**:

- **Виртуальная галерея** (`VirtualGallery.tsx`): страница `/gallery` запрашивает `GET /api/exhibits` (полный список с `include: exhibitInclude`, т.е. с `gallerySettings`), получает массив `Exhibit[]` и передаёт его в `<VirtualGallery exhibits={exhibits} />`. Внутри `exhibitData` считается в `useMemo`: для каждого экспоната берутся `galleryPositionX/Y/Z`, `galleryScale`, `galleryRotationY` (при отсутствии координат — авто-сетка по индексу). Эти значения передаются в `<ExhibitInSpace position={...} scale={...} rotationY={...} />` и далее в `<group position={position} rotation={[0, rotationY, 0]}><group scale={scale}>...</group></group>`.

- **Редактор** (`app/admin/gallery/page.tsx`): тот же источник — `exhibits` в React state после `loadExhibits()` (полный список с API). Для каждого экспоната в цикле рендера передаются `exhibitPosition`, `exhibitScale`, `exhibitRotation` из полей экспоната в `<EditableExhibit position={...} scale={...} rotationY={...} onPositionChange={...} ... />`. При перетаскивании/масштабе/повороте вызываются колбэки, которые обновляют локальный state `exhibits` (поля `galleryPositionX/Y/Z`, `galleryScale`, `galleryRotationY`); в БД ничего не пишется до нажатия «Сохранить» / «Сохранить все».

**Итог:** Данные из БД → API → React state → пропсы в R3F. Никакого отдельного глобального стейта для 3D; связь «БД ↔ сцена» только через пропсы и обновление state при сохранении.

## 2. Редактор: логика трансформации и сохранение

**Перемещение/вращение/масштаб:** TransformControls из Drei **не используются**. Реализовано ручное перетаскивание и вращение в компоненте `EditableExhibit`:

- **Перемещение:** при `pointerdown` запоминаются начальная позиция мыши (нормализованные координаты), позиция экспоната и горизонтальная плоскость `THREE.Plane` на высоте экспоната. В `pointermove` луч из камеры пересекается с плоскостью (`raycaster.ray.intersectPlane`), считается дельта от начальной точки пересечения и вызывается `onPositionChange(newPos)`. Есть режим «фиксация высоты» (`lockHeight`): тогда движение мыши по X/Y переводится в изменение мировых X и Y (высота), а не X и Z.
- **Вращение:** при зажатом Shift (или включённом переключателе «Режим вращения») в `pointermove` считается дельта мыши по X, из неё — приращение угла и вызывается `onRotationChange(normalizedRotation)`.
- **Масштаб:** меняется только из боковой панели (инпуты), не из сцены.

**Fallback при пересечении с плоскостью:** если `intersectPlane` не даёт точку (край экрана и т.п.), используется запасной вариант: дельта мыши умножается на коэффициент (например `mouseDelta.x * 5`) и прибавляется к позиции. Это может давать разную «чувствительность» по сравнению с raycast-режимом.

**Сохранение в БД:** не при каждом движении, а **по кнопкам**:
- «Сохранить» — сохраняет только **выбранный** экспонат: `PUT /api/exhibits/${exhibit.id}` с телом `{ ...exhibit, galleryPositionX, galleryPositionY, galleryPositionZ, galleryScale, galleryRotationY }`.
- «Сохранить все» — для каждого экспоната из state вызывается `PUT /api/exhibits/${ex.id}` с текущими координатами; после успеха вызывается `loadExhibits()` для обновления списка.

На бэкенде в `updateExhibitFromFlat` запись `GallerySettings` перезаписывается: `deleteMany` по `exhibitId`, затем `create` с новыми `posX/posY/posZ/scale/rotY/visibleInGallery`. Маппинг имён: в API приходят `galleryPositionX/Y/Z`, `galleryScale`, `galleryRotationY`; в Prisma — `posX`, `posY`, `posZ`, `scale`, `rotY`.

## 3. Рендеринг сцены: загрузка моделей, 10+ тяжёлых моделей

**Загрузка:** В обоих сценариях (галерея и редактор) модель подгружается через компонент `SafeModelWrapper` → `ModelLoader` с `useGLTF(normalizedPath)` из `@react-three/drei`. Каждый экспонат с `has3DModel && modelPath` рендерит свой `<SafeModelWrapper modelPath={exhibit.modelPath} />` внутри `<Suspense fallback={...}>`. **Preload** (например `useGLTF.preload`) **нигде не используется** — модели начинают грузиться только при монтировании компонента.

**Поведение при многих экспонатах:** И галерея, и редактор при открытии получают **полный** список экспонатов с 3D и рендерят их все сразу. То есть при 10+ экспонатах с тяжёлыми GLB:
- все 10+ вызовов `useGLTF` стартуют почти одновременно при первом рендере Canvas;
- нет отложенной загрузки по расстоянию до камеры (LOD или «загружать только рядом»);
- нет приоритизации (например, сначала видимые в view frustum).

`distanceToCamera` в `VirtualGallery` используется только для отображения подписи (Html) при приближении камеры (`isClose = distanceToCamera < 8`), а не для выгрузки/подгрузки моделей.

**Обработка ошибок:** Есть `ModelErrorBoundary` (в галерее — с повторной попыткой через 3 с), при ошибке показывается заглушка (серый куб). В редакторе — аналогичный `ModelErrorBoundary` без ретрая. `SafeModel` внутри делает `scene.clone()`, нормализует размер (TARGET_MAX_SIZE = 2) и центрирует по XZ и по Y; при размонтировании вызывается `disposeScene` для геометрии и материалов.

**Итог:** Suspense используется только как fallback при загрузке одной модели; массовой загрузки 10+ тяжёлых моделей специально не оптимизируют — все грузятся сразу, что может приводить к долгой первой отрисовке и всплеску памяти.

## 4. Синхронизация: какой экспонат выбран, связь ID ↔ 3D-объект

**Редактор:**
- Выбор экспоната хранится в React state: `selectedExhibitId: string | null`. При клике по экспонату вызывается `onSelect()` → `setSelectedExhibitId(exhibit.id)`. В списке в боковой панели тот же `selectedExhibitId` задаёт выбранный пункт в `<select>` и используется для «Сохранить» и отображения полей позиции/масштаба/поворота.
- Связь «объект в сцене ↔ экспонат в БД» держится **только на уровне React**: в `exhibits.map` каждый элемент рендерится как `<EditableExhibit key={exhibit.id} exhibit={exhibit} ... onSelect={() => setSelectedExhibitId(exhibit.id)} ... />`. То есть ID из БД приходит в компонент через проп `exhibit.id`; в сцене Three.js **никакого userData.exhibitId или name с ID нет** для целей выбора. В коде есть только `groupRef.current.traverse((child) => { child.userData.isExhibit = true })` — это лишь пометка «это часть экспоната», не идентификатор.
- Итог: редактор «понимает», какой экспонат выбран, только по React state и ключу в списке; raycast по объектам с привязкой к ID в userData не используется.

**Виртуальная галерея:** при клике по экспонату вызывается `onClick()` → `handleExhibitClick(exhibit.id)` → `router.push('/exhibit/${exhibitId}')`. ID снова берётся из пропа `exhibit.id`, а не из userData или ref объекта в сцене.

**Потенциальные риски:** Если бы порядок `exhibits` на сервере менялся или рендер был условным по-разному для одного и того же `exhibit.id`, теоретически возможна рассинхронизация; в текущей реализации список приходит один раз и ключи стабильны по `exhibit.id`, поэтому проблемы маловероятны при отсутствии багов в самом списке.

## 5. Честно о «костылях» и возможных багах

- **Смешение `select` и `include` в Prisma (уже исправлено):** В `exhibitListSelect` у связи `supervisor` раньше было одновременно `select` и `include` (department). Prisma это запрещает; исправлено на один `select` с вложенным `department: { select: { name: true } }`. Для полной выборки экспонатов с галереей используется `exhibitInclude` с `include`, там такого конфликта нет.

- **Два источника правды по высоте в авто-сетке:** В виртуальной галерее при отсутствии сохранённых координат позиция считается как `[x, 0, z]` (Y=0). В редакторе границы `GALLERY_BOUNDS.minY = 0.5`. Пол сцены может быть не на Y=0; если позже появятся объекты на полу, возможна визуальная рассинхронизация «авто-позиция Y=0» и реальный пол. Лучше задать единую базовую высоту (например, 0.5) и для авто-сетки.

- **Fallback при пересечении луча с плоскостью:** В редакторе при неудачном `intersectPlane` используется линейное смещение от дельты мыши с коэффициентом 5. На разных разрешениях и углах камеры это может давать разную «чувствительность» и ощущение «подлагивания» или скачка по сравнению с raycast-режимом.

- **Обновление state при каждом pointermove:** Каждое движение мыши при перетаскивании вызывает `onPositionChange` / `onRotationChange` → `setExhibits(...)` / обновление объекта в state → ре-рендер всего списка экспонатов в Canvas. При большом количестве экспонатов это может давать лаги. Вариант смягчения: хранить «черновую» позицию в ref внутри `EditableExhibit` и вызывать колбэк с throttle или только в `pointerup`.

- **Сохранение только выбранного vs «Сохранить все»:** Пользователь может подвигать несколько экспонатов, затем нажать «Сохранить» и сохранится только текущий выбранный. Остальные изменения останутся только в локальном state и пропадут при перезагрузке. Интерфейс это не подчёркивает; возможны ожидания в духе «Сохранить всё разом».

- **Десериализация JSON:** В `formatExhibit` поля `technicalSpecs` и `interestingFacts` приходят из БД как строки; при необходимости они парсятся через `JSON.parse`. Если в БД попадёт невалидный JSON, возможна ошибка при загрузке списка экспонатов. Стоит обернуть в try/catch и подставлять значения по умолчанию.

- **Публичная галерея тянет полный список:** Страница `/gallery` вызывает `GET /api/exhibits` без пагинации и получает все экспонаты с полным `exhibitInclude` (включая gallerySettings). При 1000+ экспонатах это тяжёлый ответ и большой массив в памяти; для галереи обычно нужны только экспонаты с 3D и с `visibleInGallery !== false`, и логично иметь отдельный лёгкий эндпоинт или параметр (например, `?forGallery=1`) с минимальным набором полей и пагинацией или лимитом.

- **Нет TransformControls:** Ручной raycast/plane и fallback по дельте мыши работают, но для редактора позиций стандартный подход — TransformControls (translate/rotate/scale) с привязкой к объекту; он даёт предсказуемое поведение и меньше кастомной логики с плоскостями и краевыми случаями.

## Краткая сводка

| Аспект | Реализация |
|--------|------------|
| Связь БД ↔ 3D | Пропсы: API → React state → VirtualGallery/EditableExhibit. Без Zustand/Redux. |
| Редактор: перемещение | Свой raycast по плоскости + fallback по дельте мыши. Без TransformControls. |
| Сохранение в БД | По кнопке «Сохранить» (один экспонат) или «Сохранить все» (PUT по каждому). |
| Загрузка моделей | useGLTF внутри SafeModelWrapper, Suspense по одному компоненту. Preload не используется. |
| 10+ моделей | Все грузятся при открытии сцены; LOD и отложенная загрузка по расстоянию нет. |
| Связь ID ↔ объект в сцене | Только через React: key=exhibit.id, onSelect(exhibit.id). userData только isExhibit, без exhibitId. |
| Основные риски | Лаги при частом setState при перетаскивании; тяжёлый полный GET для галереи; возможные сбои JSON.parse; разная чувствительность в fallback-режиме перемещения. |
